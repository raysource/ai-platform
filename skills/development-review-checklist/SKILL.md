# 代码评审清单（提交前自查）

## Overview
提交前的代码自查清单，逐项覆盖正确性、可读性、契约、安全、性能、测试质量与提交卫生，让作者在提交前把常见缺陷挡掉。

## When to Use
- 适用：代码即将提交，做提交前自查。
- 适用：需要一份可逐项核对的验收自检项。
- 适用：评审他人提交，作为检查维度清单。
- 不适用：架构设计评审、需求评审（各有专门流程）。

## Core Process
- 正确性：边界（空/0/负数/极值/重复/超长）与错误分支都有处理与测试；金额用整数或 decimal，时间用 UTC。
- 可读性：命名表意、函数 ≤ 一屏、嵌套 ≤ 3 层、魔法值提成常量；看不懂的代码先重构再提交。
- 契约：公开函数的入参与返回值有校验与文档（错误类型、空值语义）；不返回 `null` 与 `undefined` 混用的结果。
- 安全：所有外部输入都校验；SQL/命令参数化；日志与错误不泄露敏感数据。
- 性能：循环里不做重复查询/重复计算；批量操作先收集再处理（避免 N+1）；大数据量给分页与上限。
- 测试质量：断言具体值而不是「不抛异常」；测试之间互不依赖；失败信息能直接定位。
- 提交卫生：一次提交一件事、信息写明「为什么」；不留调试输出、注释掉的死代码、TODO 无负责人。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 边界情况线上基本碰不到 | 空/0/负数/极值/重复/超长的处理与测试是正确性的底线。 |
| 测试能通过就行，不用断言具体值 | 只断言「不抛异常」的测试会在逻辑漂移时静默通过；必须断言具体值。 |
| 先提交，回头再清理调试输出和死代码 | 调试输出与注释死代码会进主干并误导后续读者；提交前即清理。 |
| 提交大一点没关系，反正一起改的 | 一次提交一件事才可回滚、可评审；混杂提交会拖垮 review 与定位。 |
| 这个函数不用写契约文档，内部用的 | 契约（错误类型、空值语义）缺失时调用方只能猜，`null`/`undefined` 混用尤甚。 |

## Red Flags
- 有边界或错误分支没有对应测试。
- 金额用浮点存储，或时间不统一用 UTC。
- SQL/命令用字符串拼接，未参数化。
- 日志或错误信息里出现敏感数据。
- 循环内做重复查询/计算，或批量操作触发 N+1。
- 提交里混入调试输出、注释掉的死代码、无负责人的 TODO。

## Verification
- [ ] 边界（空/0/负数/极值/重复/超长）与错误分支均有处理与测试。
- [ ] 命名表意、函数 ≤ 一屏、嵌套 ≤ 3 层、魔法值已提常量。
- [ ] 公开函数有入参/返回值校验与文档，未混用 `null` 与 `undefined`。
- [ ] 外部输入已校验，SQL/命令已参数化，日志与错误无敏感数据。
- [ ] 测试断言具体值、相互独立、失败信息可定位；提交只做一件事且写明「为什么」。
