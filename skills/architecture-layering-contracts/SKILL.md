# 架构文档必须定层、定契约、定不可变项

## Overview
架构文档的价值在于把三件事钉死：层怎么分、契约长什么样、哪些决定现在不改。缺了任何一件，后续模块各自为政，实现阶段会以「文档没说」为由各写一套。

## When to Use
- 适用：产出或评审架构文档、模块边界、接口契约与数据模型时。
- 适用：判定哪些决定属于「改起来代价最大」并记录现在不改的理由时。
- 不适用：单个模块的内部实现设计、类与方法级重构。

## Core Process
以下每条都是架构文档里必须落地的条目；缺哪条就是该文档的缺口。

- **必须给源码分层清单**（低层不依赖高层：`core/domain/service/api` 这样的方向要写清），并说明每层职责与禁止事项。平台从架构产物 `ARC-01` 里解析层清单；解析不到时回落默认 `core/domain/service/api` 并在事件流里写明来源。
- **数据模型写字段级：** 字段名、类型、可空、默认值、唯一/索引、金额与时间的表示（金额用最小单位整数或 `decimal`，时间存 UTC ISO-8601）。
- **接口写契约级：** 方法、路径、请求体字段、状态码、错误码表；错误必须是枚举而不是自由文本。
- **外部依赖逐个登记：** 用途、调用频率、失败时的降级策略、超时与重试上限。
- **明确写出「改起来代价最大的决定」**（技术栈、存储、租户模型、鉴权模型），以及现在不改的理由。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 层划分实现时自然就有了 | 平台按架构产物里的层清单落位代码；不写就回落默认层，模块会被放错位置。 |
| 接口先写个大概，字段后面补 | 请求体字段与错误码表是契约的一部分；错误码后期从自由文本改成枚举要改所有调用方。 |
| 金额用 `float` 也没差 | 浮点误差在金额与对账上不可逆；金额用最小单位整数或 `decimal`，时间统一 UTC ISO-8601。 |
| 依赖超时和重试不用写进文档 | 没有超时与重试上限的依赖会拖垮整条调用链；降级策略是可用性设计的一部分。 |
| 大决定等有需求再改 | 技术栈、存储、租户模型、鉴权模型是改起来代价最大的决定；现在不改可以，理由必须写。 |

## Red Flags
- 架构文档只有目录结构，没有层职责与每层禁止事项。
- 数据模型写到「用户表」一级就停，没有字段名、类型、可空、默认值与金额/时间表示。
- 接口用自由文本描述错误（「出错时返回相应错误」），没有错误码枚举表。
- 外部依赖只在图上连了线，没有用途/频率/降级/超时与重试上限。
- 全文没有「不可变项」段落：看不到技术栈、存储、租户模型、鉴权模型的取舍与不改理由。

## Verification
- [ ] 架构产物含源码分层清单，明确低层不依赖高层的方向，并逐层写出职责与禁止事项。
- [ ] 数据模型字段级完整：字段名、类型、可空、默认值、唯一/索引，且金额与时间表示符合最小单位整数或 `decimal` + UTC ISO-8601。
- [ ] 接口契约级完整：方法、路径、请求体字段、状态码、错误码表，错误为枚举。
- [ ] 外部依赖逐个登记用途、调用频率、降级策略、超时与重试上限，无缺项。
- [ ] 「改起来代价最大的决定」段落列出技术栈、存储、租户模型、鉴权模型及现在不改的理由。
