# 开发通用规范

## Overview
给开发阶段的代码交付物定一套可执行、可单测、零惊喜的底线规范：模块单职责、依赖可追溯、行为可重复、错误不吞、命名带业务语义、必附单测，使交付物能被独立测试与规约检查，而不是靠约定与默契。

## When to Use
- 适用：编写开发阶段代码；提交/评审代码交付物；判定一个模块或函数是否符合本平台规范。
- 不适用：WBS 任务拆分与验收判据（见 `wbs-module-granularity`）、估算与排期（见 `wbs-estimate-and-dependencies`）。

## Core Process
- 一个模块只做一件事；对外只暴露必须的函数/入口，其余保持私有。
- 不引入任何未在架构文档登记的依赖；需要状态就用显式传入的数据结构，不藏全局单例。
- 时间、随机、IO 一律从参数或注入进来，函数保持可重复执行（同输入同输出）。
- 错误用返回值/异常枚举表达，绝不吞掉；每个错误分支都要有对应的测试。
- 函数短、命名动词开头、参数不超过 4 个；超过就把参数收成一个对象。
- **命名的业务语义优先**：文件名/类名/函数名用「它做什么」命名（`OrderService` / `order-service` / `order_service`），看得懂的人不需要注释。**文件名不要带 WBS 分解序号**——不写 `M1OrderService.java`、`m1_order_service.py`、`E2T1Validate.mjs`；`M1`/`E2`/`T3` 是平台内部的追踪号（用在状态机、事件流、门禁上），不进交付物。同层重名换更具体的业务名（`OrderRefundService`），而不是加数字后缀。平台的规约偏差检查会把带序号的命名记进事件流。
- 交付必须同时给单元测试：正常路径 + 边界（空/0/极值/重复）+ 错误分支，断言具体值。
- 注释只解释「为什么」，不解释「做了什么」；TODO 必须带条件与负责人。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 「先引这个库，之后再登记」 | 未登记的依赖让构建不可复现、架构文档失真；先登记再引入。 |
| 「用全局变量/单例传状态更省事」 | 隐藏状态让函数不可重复执行、单测互相污染；状态用显式传入的数据结构。 |
| 「时间/随机直接调用，测试里 mock 就行」 | 从参数注入才能保证同输入同输出；靠 mock 是在为不可测设计打补丁。 |
| 「错误先吞掉，以后再补处理」 | 吞掉的错误不可观测，问题会在最远的地方爆发；错误分支必须显式并有测试。 |
| 「文件名带 M1/T2 方便对应 WBS」 | WBS 序号是平台内部追踪号，不进交付物；带序号命名会被规约偏差检查记入事件流。 |

## Red Flags
- 一个模块承担多件事，或对外暴露了不该暴露的内部函数。
- 引入架构文档未登记的依赖，或藏有全局单例/隐藏状态。
- 函数直接调用系统时间、随机数或 IO，而非从参数注入。
- 存在被 `catch`/忽略却不处理的错误分支，或该分支没有测试。
- 文件名/类名带 `M1`/`E2`/`T3` 等 WBS 序号。
- 交付没有配套单测，或测试只覆盖正常路径。

## Verification
- [ ] 模块单职责，对外只暴露必须入口；同输入同输出的函数已确认可重复执行。
- [ ] 依赖全部在架构文档登记，无隐藏全局单例。
- [ ] 每个错误分支都有对应测试，且错误经返回值/异常枚举显式表达、未被吞掉。
- [ ] 文件名/类名/函数名为业务语义命名，无 WBS 序号；平台规约偏差检查未记录带序号命名。
- [ ] 附带单测覆盖正常路径 + 边界（空/0/极值/重复）+ 错误分支，并断言具体值且全绿。
