# 安全设计（默认拒绝）

## Overview
架构阶段的安全设计不是「记得写点安全」，而是把默认拒绝的规则落到每一层产物上：谁证明身份、谁能做什么、每个接口的范围是什么。没写进架构文档的安全约定，在代码阶段不会自己长出来。

## When to Use
- 适用：产出或评审架构文档、接口清单、权限矩阵、数据流与外部依赖登记时。
- 适用：`security-baseline` 之外需要逐接口、逐资源范围落位的架构决策时。
- 不适用：具体代码漏洞扫描、渗透测试执行、上线后的应急响应（走 `operations-incident-response`）。

## Core Process
以下每条都是架构文档里必须落地的条目；缺哪条就是该文档的缺口。

- **鉴权与授权分开写：** 谁证明身份（会话/JWT/SSO，过期与续期策略）、谁能做什么（角色→权限→资源范围的矩阵，默认拒绝）。
- **每个接口标注：** 需要的角色、数据范围（自己/本组织/全部）、是否可匿名；没有标注的接口视为漏洞。
- **输入边界：** 长度/类型/范围/枚举白名单、上传文件的类型与大小与存储位置（禁止可执行目录），统一在入口校验。
- **输出安全：** 错误信息不回传堆栈/SQL/内部 ID；跨域与内容类型显式声明；渲染用户内容要转义或白名单清洗。
- **密钥与凭据：** 只在环境变量/密钥管理里，禁止进仓库与日志；轮换周期与责任人写清楚（落地方式见 `deployment-config-and-secrets`）。
- **审计与追责：** 敏感操作（改权限、导出、删除）记审计日志（谁/何时/对象/前后值）并说明留存期限。
- **依赖风险：** 列出依赖清单与版本策略，写清漏洞响应流程（谁能升级、多久内完成）。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 权限矩阵等接口定稿再补 | 接口按权限矩阵落位，顺序反了就要回改所有接口；默认拒绝的矩阵先于接口成型。 |
| 内网系统不用标注数据范围 | 数据范围决定越权面，内网同样有跨组织的越权路径；没标注的接口视为漏洞。 |
| 密钥先写在配置里，上线前再挪 | 进过仓库与日志的密钥已经算泄露，轮换成本远高于一开始就用环境变量。 |
| 审计日志量大，先不记 | 敏感操作（改权限、导出、删除）是追责的唯一依据；留存期限可以谈，可以不记不能省。 |
| 依赖版本锁定会挡住安全更新 | 版本策略与漏洞响应流程正是为此存在：谁能升级、多久内完成写清楚即可。 |

## Red Flags
- 架构文档里出现接口清单，却没有角色 / 数据范围 / 是否可匿名三列。
- 授权只写「有权限才能访问」，没有角色→权限→资源范围的矩阵。
- 错误处理章节出现「返回详细错误方便排查」而没提堆栈/SQL/内部 ID 的脱敏。
- 上传文件的存储位置落在可执行目录，或没写类型与大小上限。
- 密钥出现在仓库文件、日志样例或架构文档正文里。

## Verification
- [ ] 架构产物文件（`workspace/<id>/docs/` 下的安全相关章节）含鉴权与授权两段：身份凭证类型 + 过期续期策略、角色→权限→资源范围矩阵。
- [ ] 接口清单每个接口都带角色 / 数据范围（自己/本组织/全部）/ 是否可匿名，无空白项。
- [ ] 输入边界与输出安全各有条目，覆盖长度/类型/范围/枚举白名单、上传文件约束、错误脱敏与转义策略。
- [ ] 密钥与凭据的存放位置、轮换周期、责任人成对出现；审计日志写明敏感操作列表与留存期限。
- [ ] 依赖清单与版本策略、漏洞响应流程（谁能升级、多久内完成）已入文档。
