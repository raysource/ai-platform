# 成本与容量治理

## Overview

让「钱花在哪、什么时候该扩容、什么时候该省」有据可查。产出物是逐条资源的账本与趋势、容量水位与扩容触发条件、成本异常告警与配额降级路径、季度优化清单，以及需求上线前的成本增量评估。

## When to Use

- 适用：盘点实例/存储/带宽/第三方调用成本，设定容量阈值与扩容动作，处理成本异常，评估需求上线带来的成本增量。
- 不适用：监控指标、告警定义、日志规范归 `operations-monitoring-runbook`；备份与恢复演练归 `operations-backup-and-restore`。容量相关的告警阈值与监控技能的指标阈值应保持一致。

## Core Process

1. 资源账本：列出每条资源（实例/存储/带宽/第三方调用）的规格、单价、月度用量与趋势，标出增长最快的三项。增长最快的三项每季度重算，不沿用上一季结论。
2. 容量水位与扩容触发条件：CPU/内存/磁盘/连接数/队列长度的告警阈值与扩容动作（谁执行、多久生效）。阈值与 `operations-monitoring-runbook` 的指标阈值对齐，扩容动作写清执行者与生效时长。
3. 成本异常告警：日环比/周环比超阈值即告警；对第三方 API 设配额上限与降级路径。降级路径要写明超配额后系统返回什么、用户看到什么。
4. 每季度做一次优化清单：可下线的资源、可降规格的实例、可合并的任务，每项给预计节省与风险。没有预计节省金额的项不算优化项。
5. 需求上线前评估成本增量（预估 QPS × 单价 + 存储增量），超过阈值需要说明取舍。取舍写清「多花多少、换来什么、不做的后果」。
6. 账本、告警与实际账单三方对账：账本单价与月度用量要能对回真实账单，偏差超过阈值要解释。

## Common Rationalizations

| 借口 | 事实 |
|---|---|
| 资源不多，脑记就行 | 增长最快的三项通常不是最贵的那三项，靠印象挑不出该优化的对象。账本的作用是发现趋势拐点。 |
| 扩容等告警响了再处理 | 没预设触发条件和生效时长，扩容会变成「先出事、再讨论、再排队」。 |
| 第三方 API 按量付费，自然有上限 | 按量付费没有上限，只有账单上限。没有配额和降级路径，一次异常流量就是一张超额账单。 |
| 优化清单先列项，金额后面补 | 没有预计节省与风险的项无法排优先级，也不会有资源去落地。 |
| 成本增量小，不用评估 | 单次增量小、频次高才是成本失控的常见路径。阈值存在的意义就是把很多个小增量拦在门口。 |

## Red Flags

- 资源账本只有规格没有单价或月度用量趋势。
- 缺「增长最快的三项」，或长期未重算。
- 容量阈值与监控技能里的指标阈值不一致。
- 第三方 API 无配额上限或降级路径描述。
- 需求上线材料里没有任何成本增量数字。
- 账本与真实账单从未对账。

## Verification

- [ ] 资源账本覆盖每条实例/存储/带宽/第三方调用，含规格、单价、月度用量与趋势。
- [ ] 明确标出增长最快的三项，且为本季度重算结果。
- [ ] 容量水位阈值齐全（CPU/内存/磁盘/连接数/队列长度），每项含扩容动作、执行者与生效时长。
- [ ] 成本异常告警有日/周环比阈值，第三方 API 有配额上限与降级路径。
- [ ] 季度优化清单每项都有预计节省与风险。
- [ ] 至少一份需求上线前的成本增量评估（预估 QPS × 单价 + 存储增量），超阈值的有取舍说明。
