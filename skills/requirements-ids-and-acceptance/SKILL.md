# 需求编号与验收

## Overview
需求必须可编号、可验收：每条需求有稳定编号，每个编号下挂可复核的验收标准，范围、依赖与冲突都显式写出。做不到这些，后续的 WBS、估算与测试判据都会悬空。

## When to Use
- 适用：需求阶段——编写或评审需求列表、用户故事、验收标准、范围与依赖时。
- 不适用：需求基线已冻结、只做实现编码时；架构、测试或运维阶段的技术设计。

## Core Process

### 编号与正文
- 每条需求必须有稳定编号 `REQ-NN`，正文写清「谁 / 在什么条件下 / 期望什么结果」。
- 用户故事按 `US-NN` 编号，格式「作为<角色>，我要<能力>，以便<价值>」，并挂上它覆盖的 `REQ` 号。

### 验收标准
- 每个编号下面挂至少一条验收标准 `AC-NN`，判定方式必须可机器或可人工复核（给数字、给边界、给触发条件）。
- 禁止「体验良好」「性能高」这类无判定词。

### 范围、依赖与冲突
- 范围要显式：列出本期不做（Out of scope）与依赖（外部系统、数据、审批）。
- 冲突与歧义单独列一节：写清候选解释与需要谁拍板，不要在心里替用户选。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 需求先写成一句话，验收回头再补 | 没有 `AC-NN` 的需求无法复核，后续 WBS 与测试判据会悬空。 |
| 用户故事编号太啰嗦，能看懂就行 | 没有 `US-NN` 与 `REQ` 的关联，需求覆盖追踪会出现盲区。 |
| 范围大家心里有数，不用写不做的事 | 不写 Out of scope 与依赖，需求会在后期无限膨胀。 |
| 冲突让用户自己选就好 | 冲突必须登记候选解释与拍板人，不得在心里替用户选。 |

## Red Flags
- 出现无编号的散落需求条目。
- `AC-NN` 用了「体验良好」「性能高」等无判定词。
- 需求列表缺 Out of scope / 依赖清单。
- 冲突被随手抹平、没有拍板人记录。

## Verification
- [ ] 需求列表每条都有 `REQ-NN`，无跳号、无重号。
- [ ] 每个 `REQ-NN` 下至少一条 `AC-NN`，且判定方式给出数字/边界/触发条件。
- [ ] 每条用户故事有 `US-NN` 且挂上覆盖的 `REQ` 号。
- [ ] 有显式的 Out of scope 与依赖清单。
- [ ] 冲突与歧义单独成节，写明候选解释与拍板人。
- [ ] 产物文件已落盘、事件流里可见需求阶段产出记录。
