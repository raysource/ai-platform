# 备份、恢复与演练

## Overview

备份的价值不在「有备份」，而在「能按时恢复回来」。产出物是逐数据集的备份策略表、明确的 RPO/RTO、能照着执行的恢复步骤、季度演练记录（含真实耗时与失败点），以及备份有效性和过期数据清理的闭环。

## When to Use

- 适用：制定或评审备份策略、定义 RPO/RTO、编写恢复步骤/脚本、安排恢复演练、处理过期数据保留与清理。
- 不适用：监控指标、告警定义、日志规则归 `operations-monitoring-runbook`；容量水位与成本账本归 `operations-cost-and-capacity`。

## Core Process

1. 备份策略逐数据集写：频率（全量/增量）、保留周期（按天/周/月分层）、存放位置（异地/跨账号）、加密与访问权限。每个数据集单独一行，不允许「所有数据统一每天一次」这种合并描述。
2. 明确 RPO/RTO：能丢多少数据、多久恢复；不一致就说明差距与补齐计划。业务要求与现状对不上时，写清差距数值与补齐时间点，而不是把现状倒填成要求。
3. 恢复步骤必须是可执行脚本或编号步骤（含权限与依赖顺序），不做「从备份恢复」这种无法操作的描述。步骤里明确谁有权限、先起什么后起什么、到哪一步可以对外恢复服务。
4. 演练：每季度至少一次真实恢复到独立环境，记录实际耗时、失败点与修复项；演练前先记录基线。演练环境独立于生产，恢复目标不与生产共享存储。
5. 备份有效性验证：定期校验备份可读与校验和，告警规则覆盖「备份任务失败」「备份大小异常」。只记录备份成功日志不算验证，必须真的读取并校验。
6. 数据删除与保留：过期数据按合规要求清理，清理前确认已备份且不可逆操作有审批。审批留痕，删前与删后各留一条记录。
7. 演练失败点必须回灌到步骤或策略：每次演练发现的问题要么改步骤、要么改策略、要么进整改清单，不能只写在报告的「备注」里。

## Common Rationalizations

| 借口 | 事实 |
|---|---|
| 有每日全量备份就安全了 | 备份任务失败、文件损坏、保留周期被覆盖，任何一项都会让「有备份」变成不可用。没做过读取校验和恢复演练，等于没有备份。 |
| RPO/RTO 按现状写就行 | 把现状当要求，差距永远不会被补齐。RPO/RTO 是业务约束，对不上时必须写差距与计划。 |
| 恢复流程写「从备份恢复数据」即可 | 这种描述在故障现场无法执行。缺权限顺序和依赖顺序，恢复时间会花在试错上。 |
| 演练放到有窗口的时候再做 | 「有窗口」通常永远不会来。季度演练是排期项，不是等空闲项。 |
| 过期数据清理是运维日常，不用审批 | 不可逆删除必须留审批：删错一次无法回滚，且可能违反合规保留要求。 |

## Red Flags

- 备份策略没有逐数据集拆分，或缺少保留周期分层。
- RPO/RTO 只是「越快越好」，没有数值。
- 恢复步骤里出现「从备份恢复」而无权限/依赖顺序。
- 演练记录只有日期，没有实际恢复耗时和失败点。
- 备份有效性只靠任务成功日志，没有读取校验或校验和。
- 存在无审批记录的不可逆删除操作。

## Verification

- [ ] 每个数据集都有独立一行备份策略，含频率、保留分层、存放位置、加密与访问权限。
- [ ] RPO/RTO 有具体数值，且业务要求与现状的差距有补齐计划。
- [ ] 恢复步骤为编号步骤或脚本，含权限与依赖顺序，可脱离原作者被执行。
- [ ] 有最近一次季度演练记录：独立环境、实际耗时、失败点、修复项，且演练前基线已记录。
- [ ] 存在备份读取/校验和的验证记录，且告警规则覆盖「备份任务失败」与「备份大小异常」。
- [ ] 过期数据清理条目附审批留痕，且清理前确认已备份。
