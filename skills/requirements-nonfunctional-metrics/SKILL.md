# 非功能需求指标化

## Overview
非功能需求（性能 / 容量 / 合规）必须指标化：给出数字、条件与测量点，并写明验收方式。没有测量手段的需求等于没有需求。

## When to Use
- 适用：需求阶段——定义或评审性能、容量、可用性、合规与隐私指标时。
- 不适用：纯功能需求的描述；实现与运维阶段的具体调优。

## Core Process

### 性能
- 性能给数字与条件：页面 `P95 ≤ ?ms`、接口 `P95 ≤ ?ms @ 并发 ?`、批量任务 `≤ ? 分钟/万条`；写清测量点（浏览器/网关/DB）与数据量级。

### 容量
- 容量给量级：日活/峰值 QPS、单条记录大小、年增量、留存年限；由此推出存储与备份规模（写算式，不写「足够大」）。

### 可用性
- 可用性给目标与代价：可用性 %（99.5 / 99.9）、允许的月度不可用时间、降级方案（哪些功能可以只读/排队）。

### 合规与隐私
- 合规与隐私：涉及哪些个人/敏感数据、依据哪条法规、留存与删除要求、是否跨境；不确定就标「待法务确认」并写清阻塞影响。

### 验收方式
- 每个非功能需求都写验收方式：压测脚本、监控面板、审计报告 —— 没有测量手段的需求等于没有需求。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 性能需求等压测时再看 | 没有数字与测量点，压测就没有目标；`P95` 与并发条件必须先写清。 |
| 存储说「足够大」就行 | 容量要用日活/峰值 QPS、记录大小、年增量等写算式推出存储与备份规模。 |
| 可用性做到 99.9 就够了 | 除百分比外，还要给出允许的月度不可用时间与降级方案。 |
| 合规待法务确认就先搁置 | 标「待法务确认」时必须写清阻塞影响，不能只挂一句待定。 |
| 有监控面板就说明需求达标 | 压测脚本 / 监控面板 / 审计报告三选一都可，但必须有测量手段。 |

## Red Flags
- 性能写成「快」「高吞吐」等无数字描述。
- 容量用「足够大」代替算式。
- 可用性只有百分比、没有不可用时间与降级方案。
- 非功能需求没有任何测量手段。
- 合规与隐私只写「待法务确认」而不写阻塞影响。

## Verification
- [ ] 每条性能需求有 `P95` 数字、并发条件与测量点（浏览器/网关/DB）。
- [ ] 容量给出日活/峰值 QPS、记录大小、年增量、留存年限，并用算式推出存储/备份规模。
- [ ] 可用性给出目标 %（如 99.5 / 99.9）、月度不可用时间与降级方案。
- [ ] 合规与隐私列明数据类型、法规依据、留存/删除要求、是否跨境；不确定项标「待法务确认」且有阻塞影响。
- [ ] 每条非功能需求都写明验收方式（压测脚本 / 监控面板 / 审计报告）。
- [ ] 产物文件与事件流可见需求阶段非功能指标的记录。
