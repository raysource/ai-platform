# 部署方案要可回滚、可验证

## Overview
把一次发布写成别人能照着执行、出问题能照着回退的文档。核心是环境矩阵、带验证输出的发布步骤、明确触发条件的回滚方案，以及发布后的冒烟清单。

## When to Use
- 适用：为一次上线编写部署方案；梳理环境矩阵与配置来源；设计回滚步骤与触发条件；定义变更窗口与冒烟清单。
- 不适用：设计流水线阶段、制品晋升与灰度比例（见 deployment-pipeline-and-canary）；调试构建脚本、CI 配置语法本身。

## Core Process
1. 写清环境矩阵：环境名、域名/入口、数据库、依赖服务、配置来源（哪些走环境变量、哪些走配置中心）。
2. 发布步骤按「先做什么再做什么」编号，每步给出验证命令与期望输出（含健康检查路径与状态码）。
3. 必须给回滚方案：回滚触发条件、回滚步骤、数据是否兼容（向前/向后兼容的变更方式：先加字段后删字段）。
4. 配置与密钥不落仓库：列出全部配置项、示例值、必填与默认，说明从哪里注入。
5. 变更窗口与影响面：是否需要停机、是否有不可用时段、谁来通知用户。
6. 冒烟清单：发布后必须验证的 5–10 条（登录、主流程、关键写操作、日志与告警已上报）。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 回滚方案等出问题再说 | 没有触发条件和步骤，事故现场才开始想，恢复时间成倍拉长。发布前必须写好。 |
| 配置项列个大概就行 | 缺一个必填项就是一次上线失败；示例值与必填/默认必须逐条列全。 |
| 冒烟清单先跳过 | 5–10 条冒烟是发布后唯一能立刻发现「上线即坏」的手段，跳过等于拿用户当测试。 |
| 环境差异先不管 | 预发与生产的中间件版本、配置结构不一致，问题只在生产暴露，回滚也难定位。 |

## Red Flags
- 发布步骤没有期望输出或健康检查状态码，只有「部署一下」。
- 回滚方案缺失或只写「回滚到上一版本」，没有触发条件与数据兼容说明。
- 配置或密钥出现在仓库里，或配置项清单不完整。
- 没有变更窗口与用户通知安排。

## Verification
- [ ] 环境矩阵覆盖环境名、入口、数据库、依赖服务、配置来源。
- [ ] 每条发布步骤都有验证命令与期望输出（含健康检查路径与状态码）。
- [ ] 回滚方案含触发条件、步骤、数据向前/向后兼容说明。
- [ ] 全部配置项、示例值、必填与默认、注入来源已列全，且仓库中无密钥。
- [ ] 冒烟清单 5–10 条，覆盖登录、主流程、关键写操作、日志与告警。
