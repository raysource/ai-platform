# 运维：可观测、可定位、可恢复

## Overview

把「上线后能不能发现问题、能不能定位、能不能恢复」写成可核对的条目，而不是一句「已配置监控」。产出物是四类指标及阈值、每个告警的处置与升级、日志三条规则、巡检与排查手册、变更记录。

## When to Use

- 适用：设计或评审监控指标、告警规则、日志规范；编写运维手册与故障排查树；建立发布/配置变更记录。
- 不适用：备份策略与恢复演练归 `operations-backup-and-restore`；容量水位与成本账本归 `operations-cost-and-capacity`；故障发生后的时间线与复盘归 `operations-incident-response`。

## Core Process

1. 监控指标按四类给：流量（QPS/并发）、错误（错误率/错误码分布）、延迟（P50/P95/P99）、饱和度（CPU/内存/连接池/队列长度），每项给阈值与告警级别。四类缺一不可，只给 CPU 一项不算监控方案。
2. 每个告警写：触发条件、影响、第一处置动作、升级路径与责任人角色；禁止只写「告警通知」。一条合格的告警定义至少能回答「收到它之后第一步做什么、多久没恢复该找谁」。
3. 日志三条规则：结构化（可 JSON 解析）、带请求 ID 贯穿链路、不落敏感信息（密码/令牌/身份证）。
4. 运维手册覆盖：日常巡检项与频率、备份与恢复演练步骤（含恢复耗时目标）、常见故障的排查树（从症状到命令）。排查树的每条边落到具体命令，不写「检查一下服务状态」。
5. 发布与配置变更记入变更记录：谁、何时、改了什么、如何验证、是否需要复盘。变更记录与告警时间线对齐，事后才能解释「这条曲线为什么从这一刻开始变」。
6. 指标、告警、日志、巡检项之间要能对应：告警触发的指标必须在巡检或看板里可见，排查树引用的日志字段必须真的能查到。

## Common Rationalizations

| 借口 | 事实 |
|---|---|
| 先上 CPU 和内存告警，其他类后面补 | 少任何一类，故障都落在盲区：错误率看不见就是用户先发现，延迟分位缺失就看不出「整体正常但长尾挂了」。 |
| 告警写「通知值班群」就够了 | 通知不是处置。没有第一动作和升级路径，收到告警的人要现场重建上下文，恢复时间翻倍。 |
| 日志现在人看得懂就行，结构化以后再说 | 事后补结构化要重放全量日志改采集端；上线前一条 `JSON` 输出规则比上线后一次日志迁移便宜得多。 |
| 变更是小改动，不用记 | 小改动恰恰是「曲线突变」的常见成因。不记变更，排查时只能靠猜，复盘也无从落笔。 |
| 请求 ID 会泄露内部信息 | 请求 ID 是随机标识，不是敏感数据；该禁的是密码/令牌/身份证，别拿安全当不贯穿链路的理由。 |

## Red Flags

- 指标只有资源类（CPU/内存），没有流量、错误、延迟。
- 告警条目里没有任何处置动作或责任人角色。
- 日志是拼接字符串，或同一请求在不同服务里找不到同一个 ID。
- 巡检表没有频率，或排查树终点是「联系运维」而不是一条命令。
- 变更记录缺失，或只有「改了什么」没有「如何验证」。

## Verification

- [ ] 四类指标各有阈值与告警级别，条目可在同一份监控配置里逐条指认。
- [ ] 每个告警含触发条件、影响、第一处置动作、升级路径与责任人角色。
- [ ] 抽取一条真实日志样例，可被 JSON 解析，且含贯穿链路的请求 ID。
- [ ] 日志样例中 grep 不到密码/令牌/身份证字段。
- [ ] 运维手册含巡检项与频率、恢复耗时目标、至少一棵症状到命令的排查树。
- [ ] 变更记录含至少一条完整条目（谁、何时、改了什么、如何验证、是否复盘）。
