# WBS 模块粒度与验收

## Overview
把 WBS 拆到「可独立测试的模块」这一最小粒度，并让每个 Task 自带可执行的验收判据与显式依赖，使任务在无上下文交接的情况下可被单独实现、单独验证、单独判定完成。

## When to Use
- 适用：把需求/架构分解为 WBS Task；为 Task 编写 acceptance 判据；判断某个 Task 是否还应继续拆；评审任务粒度与依赖是否合理。
- 不适用：估算工期与工时（三点估算）、标定关键路径、管理外部依赖与排期——这些走 `wbs-estimate-and-dependencies`。

## Core Process
- 一个模块 = 一个人能在一轮里写完 + 能独立跑单测的最小单元；跨模块共享的逻辑先抽成公共模块再被依赖。
- 每个 Task 必须写 acceptance：可执行的判定（输入 → 期望输出，含边界与错误分支），不要写「完成界面」。
- 依赖显式化：Task 之间谁先谁后、可否并行；被依赖方未完成时依赖方不得声称完成。
- 每个模块标出它落在哪一层目录、产物文件路径与测试文件路径。
- 不把「重构」「优化」当 Task，除非写出可测量的前后指标。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 「模块先粗一点，实现时再拆」 | 粒度没定就写不出可执行 acceptance，粗模块的验收必然退化成「界面做完了」。 |
| 「acceptance 写一句『功能正常』就够」 | 不可执行的判据无法被门禁或单测判定，等于没有验收，边界与错误分支会全部漏掉。 |
| 「依赖关系实现时自然就知道了」 | 依赖不显式化，被依赖方未完成时依赖方会照样声称完成，返工在集成时才暴露。 |
| 「这是个重构，顺手当 Task 做了」 | 无前后指标的「重构/优化」是范围黑洞，不能核算、不能验收，必须补可测量指标或另立。 |

## Red Flags
- Task 的 acceptance 里出现「完成界面」「功能可用」这类无判据表述。
- 一个 Task 塞了多件事，任何单测都无法只针对它运行。
- Task 之间没有声明先后/并行关系，或存在循环依赖。
- 出现「重构」「优化」Task 却没有前后对比指标。
- 模块没标目录层级、产物文件路径或测试文件路径。

## Verification
- [ ] 每个 Task 的 acceptance 都是「输入 → 期望输出」，含边界与错误分支，可在单测中直接断言。
- [ ] 每个模块的测试文件路径存在，且单测能只针对该模块独立运行并全绿。
- [ ] 任务依赖图无环，串行/并行关系显式声明。
- [ ] 每个模块标注了目录层级、产物文件路径与测试文件路径。
- [ ] 不存在无前后指标的「重构/优化」Task。
