# 流水线、制品与灰度

## Overview
把「代码提交到生产上线」这条路径固定成可预测、可追溯的流水线，并规定制品只构建一次、各环境晋升同一份，以及灰度与批准门禁的规则。

## When to Use
- 适用：设计流水线阶段与失败策略；制定制品版本与晋升规则；统一预发与生产环境；选择发布方式（全量/滚动/蓝绿/金丝雀）；定义批准门禁与发布回执。
- 不适用：为一次发布写环境矩阵、回滚步骤与冒烟清单（见 deployment-release-and-rollback）；写业务代码或排查 CI 脚本语法错误。

## Core Process
1. 流水线阶段固定：拉代码 → 依赖安装（可缓存）→ 静态检查/单测 → 构建制品 → 集成测试 → 部署到预发 → 人工批准 → 生产；每阶段失败即停。
2. 制品可追溯：版本号不可重复（语义化或 commit+构建号），制品只构建一次、各环境晋升同一份，禁止各环境各自构建。
3. 环境一致性：预发与生产的中间件版本、配置结构、运行参数一致（差异逐条登记）。
4. 发布方式写清：全量 / 滚动 / 蓝绿 / 金丝雀（比例与观察时长）；数据库变更与应用发布解耦（先兼容后切换）。
5. 门禁：谁批准、看什么证据（测试报告/压测结果/变更影响）、批准记录留在哪里。
6. 每次发布留回执：版本、时间、操作者、变更项、冒烟结果、异常与后续动作。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 各环境各自构建更快 | 各自构建产出的制品不一致，预发过了生产仍可能挂；必须同一份制品逐级晋升。 |
| 版本号重复无所谓 | 版本号重复就无法回溯线上跑的是哪次构建，回滚和定位都失去依据。 |
| 灰度比例凭感觉 | 没有比例与观察时长，灰度无法判定成功还是失败，等于全量发布。 |
| 批准门禁先绕过 | 无记录的口头批准无法追责，也无法在事故复盘时说明放行依据。 |

## Red Flags
- 各环境各自构建制品，或版本号可重复。
- 预发与生产的中间件版本、配置结构不一致却未登记。
- 数据库变更与应用发布耦合，无法先兼容后切换。
- 没有批准门禁记录或发布回执。

## Verification
- [ ] 流水线阶段与「每阶段失败即停」已明确。
- [ ] 制品版本号不可重复，且各环境晋升同一份。
- [ ] 预发与生产的差异已逐条登记。
- [ ] 发布方式含比例与观察时长，数据库变更与应用发布解耦。
- [ ] 门禁含批准人、证据、记录位置；每次发布有回执（版本/时间/操作者/变更项/冒烟结果/异常）。
