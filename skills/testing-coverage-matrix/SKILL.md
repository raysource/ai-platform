# 集成测试按风险排序、可重复执行

## Overview
让测试计划可核对、可复跑：用覆盖矩阵暴露缺口，用分层与通过判据定义每层边界，用可重置的环境与数据保证重复执行结果一致。

## When to Use
- 适用：编写测试计划与覆盖矩阵；划分单元/集成/端到端分层与运行命令；定义通过判据、失败定位方式与出口标准。
- 不适用：编写具体单元测试代码；制定部署方案、流水线或回滚策略（见 deployment-release-and-rollback、deployment-pipeline-and-canary）。

## Core Process
1. 测试计划列出覆盖矩阵：需求编号 × 测试用例编号，缺覆盖的格子必须写明理由（不测的代价是什么）。
2. 分层：单元（纯逻辑）/ 集成（模块间契约）/ 端到端（主路径 + 关键异常），每层给通过判据与运行命令。
3. 每个用例写：前置数据、操作步骤、期望结果（可断言）、失败时怎么定位（看哪个日志/哪条记录）。
4. 环境与数据可重置：测试数据脚本、清理步骤、幂等约束（重复跑结果一致）。
5. 明确出口标准：哪些用例必须全绿、哪些允许带已知问题上线（并给出跟踪单号）。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 覆盖矩阵留几个空格没关系 | 空格就是未验证的需求，写清理由才知道代价；不写等于默认为零代价。 |
| 用例只写期望结果 | 缺前置数据、步骤与失败定位，用例失败时无从复现、无从排查，等于没写。 |
| 测试数据手动准备 | 手工数据不可重置、不可重复，第二次运行就会因脏数据失败。 |
| 出口标准先含糊 | 不写明哪些必须全绿、哪些可带问题上线，发布时无人能判断能否放行。 |

## Red Flags
- 覆盖矩阵有空格且未写明不测理由。
- 用例缺前置数据、操作步骤、可断言期望或失败定位方式。
- 测试数据无脚本、无清理步骤，或重复执行结果不一致。
- 出口标准缺失，或允许带问题上线却无跟踪单号。

## Verification
- [ ] 覆盖矩阵为需求编号 × 用例编号，空格均写明不测理由。
- [ ] 三层测试各给通过判据与运行命令。
- [ ] 每个用例含前置数据、操作步骤、可断言期望、失败定位方式。
- [ ] 测试数据脚本与清理步骤可重置环境，重复执行结果一致。
- [ ] 出口标准明确（必须全绿项、允许带问题上线项及跟踪单号）。
