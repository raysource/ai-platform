# 故障响应与复盘（On-call 手册）

## Overview
故障现场的纪律是：先分级、再止损、后定位，边处理边留痕，对外口径统一；P0/P1 在恢复后 48 小时内完成复盘，每条改进项有负责人与截止时间并追踪到验收证据。本技能规定这套动作的顺序与最低标准。

## When to Use
- 适用：线上告警触发、核心或主要功能不可用、数据风险、需要定级与组织响应、需要做故障复盘与改进追踪。
- 不适用：监控指标与告警阈值的日常配置（用 `operations-monitoring-runbook`）；发布与回滚流程设计（用 `deployment-release-and-rollback`）；容量与成本规划（用 `operations-cost-and-capacity`）。

## Core Process
1. 分级先说清：P0（核心不可用/数据风险）、P1（主要功能受损）、P2（局部异常），各级给响应时限与通知范围。
2. 响应四步固定：止损（回滚/降级/限流）→ 定位（看哪个指标先异常）→ 修复（最小改动）→ 验证（冒烟 + 指标回落）。
3. 时间线留痕：从第一次告警到恢复，记录每一步动作与观察结果（谁、何时、做了什么、看到什么）。
4. 沟通机制：谁对外通知、多久更新一次、用什么渠道；对用户口径统一（说影响与预计恢复，不猜原因）。
5. 复盘（P0/P1 必做，恢复后 48h 内）：事实时间线、根因（技术 + 流程）、影响面（用户/数据/金额）、改进项（每条有负责人与截止时间）。
6. 改进项追踪到验收：修完要有验证证据（新增监控、回归用例、演练记录），否则复盘等于没做。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 先上手救火，定级和通知回头补 | 不定级就没有响应时限与通知范围，救火节奏失控；定级是响应第一步，不是事后文书。 |
| 原因还没确认，先跟用户说清楚 | 对外口径只说影响与预计恢复，不猜原因；猜错会二次伤害信任。 |
| 排查过程我都记得，不用逐条记 | 记忆在跨时区、换班与多线程排查下必然失真；时间线必须实时留痕（谁/何时/做了什么/看到什么）。 |
| 问题恢复了，复盘改天再约 | P0/P1 复盘必须在恢复后 48h 内做，细节会随时间流失，越晚越只能写出「流程问题」这种空话。 |
| 改进项已经开单，就算闭环了 | 开单不等于修完；必须追踪到验收证据（新增监控、回归用例、演练记录），否则同类故障会再来一次。 |

## Red Flags
- 故障已经开始处理，但等级未定、通知范围与时限不明。
- 先定位根因再止损，导致影响面持续扩大。
- 时间线靠事后回忆拼凑，缺少「谁/何时/做了什么/看到什么」四要素。
- 对外口径中出现未经确认的原因猜测。
- P0/P1 超过 48h 未复盘，或复盘只写现象无根因（技术 + 流程）。
- 改进项无负责人或无截止时间，或有单无验收证据。

## Verification
- [ ] 故障等级（P0/P1/P2）已判定，并对照到响应时限与通知范围。
- [ ] 响应过程呈现「止损 → 定位 → 修复 → 验证」四步，且验证含冒烟与指标回落证据。
- [ ] 时间线从第一次告警到恢复连续无断档，每步含谁/何时/做了什么/看到什么。
- [ ] 对外通知渠道与更新频率明确，用户口径只含影响与预计恢复，无原因猜测。
- [ ] P0/P1 在恢复后 48h 内产出复盘：事实时间线、根因（技术+流程）、影响面（用户/数据/金额）、改进项。
- [ ] 每条改进项有负责人与截止时间，并附验收证据（新增监控、回归用例或演练记录）。
