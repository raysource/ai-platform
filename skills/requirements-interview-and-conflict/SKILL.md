# 访谈与冲突裁决

## Overview
干系人访谈、冲突与变更都要有可追溯的记录：访谈输出可复核的问答、冲突显式登记、需求变更走同一张表。口头结论与口头变更一律不认，否则后面会反复重开。

## When to Use
- 适用：需求阶段——组织干系人访谈、登记需求冲突、处理需求变更时。
- 不适用：需求已冻结且无干系人分歧的编码阶段。

## Core Process

### 干系人表
- 开工前列干系人表：角色、关注点、决策权限（谁能拍板范围/预算/上线）、参与方式与频率。

### 访谈记录
- 访谈输出「问题 → 回答 → 结论/待定」，每个待定项给负责人与截止时间；不要用「用户说」当结论，写清是谁、什么时候、什么原话。

### 冲突登记
- 冲突显式登记：冲突点、各方诉求、影响面、候选方案与代价，以及最终裁决人；被否决的方案也要留痕（避免下次重开）。

### 需求变更
- 需求变更走同一张表：变更编号、原因、影响的需求/工作量/排期、批准人；口头变更一律不认。

### 假设与风险
- 假设与风险分开列：假设（如果错了会怎样、怎么验证）+ 风险（概率×影响、缓解动作、触发信号）。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 访谈记个大概就行 | 必须输出「问题 → 回答 → 结论/待定」，待定项要落到负责人与截止时间。 |
| 「用户说」就是结论 | 要写清是谁、什么时候、什么原话，不能用「用户说」当结论。 |
| 被否的方案不用留痕 | 被否决的方案也要留痕，避免同样的冲突下次重开。 |
| 口头变更先做了再补 | 口头变更一律不认，变更必须走同一张表并写批准人。 |
| 假设和风险一起列省事 | 假设（错了会怎样、怎么验证）与风险（概率×影响、缓解动作、触发信号）要分开列。 |

## Red Flags
- 访谈记录只有结论、没有原话与待定项负责人。
- 出现未登记的冲突或口头变更。
- 被否决的方案无留痕。
- 假设与风险混在一起、缺验证方式或缓解动作。

## Verification
- [ ] 干系人表列出角色、关注点、决策权限、参与方式与频率。
- [ ] 访谈记录为「问题 → 回答 → 结论/待定」，待定项有负责人与截止时间。
- [ ] 冲突登记含冲突点、各方诉求、影响面、候选方案与代价、最终裁决人，且被否方案有留痕。
- [ ] 需求变更表含变更编号、原因、影响的需求/工作量/排期、批准人。
- [ ] 假设与风险分列，假设含「错了会怎样/怎么验证」，风险含 概率×影响、缓解动作、触发信号。
- [ ] 产物文件与事件流可见需求阶段访谈与裁决记录。
