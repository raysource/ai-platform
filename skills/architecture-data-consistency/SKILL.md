# 数据模型与一致性设计

## Overview
数据层是后面所有模块共用的地基：主键、约束、事务边界一旦定错，改的是每一条读写路径。架构阶段就要把一致性边界和迁移步骤写死，让实现阶段有据可依、可独立回滚。

## When to Use
- 适用：产出或评审数据模型、表结构、迁移方案、并发写与幂等设计时。
- 适用：判断某个操作必须同事务还是允许最终一致、需要哪种锁时。
- 不适用：具体 ORM / SQL 实现细节、索引在线重建的执行操作与线上慢查询调优。

## Core Process
以下每条都是架构文档里必须落地的条目；缺哪条就是该文档的缺口。

- **每张表/实体给：** 主键策略（自增 vs UUID，理由）、唯一约束、外键与级联规则、软删除字段与查询影响。
- **一致性边界写清：** 哪些操作必须同事务（列出来）、哪些允许最终一致（给出对账/补偿任务与容忍延迟）。
- **写操作必须幂等：** 给幂等键（业务唯一号/请求 ID）与重复提交的返回语义（返回首次结果，不报 500）。
- **并发：** 明确乐观锁（版本号）还是悲观锁（行锁），锁的对象与持有时长；热点更新要有排队或分片方案。
- **迁移策略：** 先加列（可空）+ 回填 + 双写/双读 + 切流 + 删旧列，每步都可独立回滚；大表变更写清影响行数与锁级别。
- **索引：** 按查询写出索引清单（列顺序 + 选择原因），并写明哪些查询做了全表扫描的兜底（限制条件/分页上限）。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 事务边界跑起来再调整 | 事务边界决定对账与补偿任务是否存在；实现阶段再改要重写全部写路径。 |
| 幂等键用户重复点两次再说 | 重复提交是常态（重试、双击、超时重发）；返回首次结果不报 500 必须在契约里写明。 |
| 迁移一次改到位更省事 | 一步到位的迁移无法独立回滚；先加列 + 回填 + 双写/双读 + 切流 + 删旧列每步都可单独回退。 |
| 表不大，加索引随便定 | 索引清单要按查询给出列顺序与选择原因，否则实现阶段按猜加索引，反而拖慢写入。 |
| 软删除就是加个 `deleted_at` | 软删除字段会改变所有查询语义；查询影响不写清，历史数据会在列表里冒出来。 |

## Red Flags
- 表结构里出现自增主键但没写选型理由，或定义了唯一约束却说不出业务唯一键。
- 写接口没有幂等键，或重复提交语义写成「返回 500 让客户端重试」。
- 并发章节只写「加锁」而不写锁的对象、持有时长与热点排队方案。
- 迁移方案是一个大 `ALTER`，没有可独立回滚的分步与影响行数/锁级别估算。
- 索引清单与查询对不上：列出的索引没有对应查询，或已知全表扫描没有兜底限制。

## Verification
- [ ] 数据模型产物（`workspace/<id>/docs/` 下）每张表都带主键策略与理由、唯一约束、外键与级联规则、软删除字段及查询影响。
- [ ] 一致性边界列出「必须同事务」的操作清单，以及「允许最终一致」的对账/补偿任务与容忍延迟。
- [ ] 每个写操作有幂等键（业务唯一号/请求 ID）与重复提交返回语义（返回首次结果，不报 500）。
- [ ] 并发策略写明乐观锁（版本号）或悲观锁（行锁）、锁对象与持有时长；热点更新有排队或分片方案。
- [ ] 迁移按「加列 + 回填 + 双写/双读 + 切流 + 删旧列」分步写出，每步可独立回滚，并标出大表变更的影响行数与锁级别。
- [ ] 索引清单逐条给出列顺序与选择原因，全表扫描查询写明限制条件或分页上限。
