# 可用性检查表

## Overview
每个界面交付前都要过一遍这份检查表：状态可见、用户可控、一致、防错、易识别、错误可读、路径高效。任何一条不过，界面就不算交付完成。

## When to Use
- 适用：UX 阶段——界面交付前的可用性自检或评审时。
- 不适用：视觉风格选型与品牌设计讨论。

## Core Process

### 系统状态可见
- 系统状态可见：耗时操作给进度或骨架屏，`>1s` 给反馈，`>10s` 说明还要多久；任何操作都有结果反馈。

### 用户可控
- 用户可控：可撤销/可返回、删除有二次确认、输入有草稿保护（刷新/断线不丢）。

### 一致性
- 一致性：同类操作用同样的词与位置（保存/提交别混用）；危险操作用危险样式且不与主按钮相邻。

### 防错优先于纠错
- 防错优先于纠错：默认值合理、格式约束前置（输入时就拦）、只读项明确置灰而不是提交后报错。

### 识别优于记忆
- 识别优于记忆：选择项给出可读标签而不是只给编码；关键上下文（谁/哪个项目）始终可见。

### 错误信息
- 错误信息说三件事：哪里错了、为什么、怎么改；错误定位到具体字段。

### 效率
- 效率：高频路径 `≤3` 步、支持键盘操作（`Tab` 顺序合理、回车提交）、批量操作有全选与部分失败回执。

## Common Rationalizations
| 借口 | 事实 |
|---|---|
| 加载这么久用户能等 | `>1s` 就要给反馈、`>10s` 要说明还要多久；任何操作都要有结果反馈。 |
| 删除一步到位更快 | 删除要有二次确认，且要可撤销/可返回、输入有草稿保护。 |
| 出错再提示就行 | 防错优先于纠错：格式约束前置、只读项提前置灰，而不是提交后报错。 |
| 用编码让用户自己认 | 识别优于记忆，选择项要给可读标签，关键上下文要始终可见。 |
| 错误说「操作失败」够了 | 错误信息要说清哪里错了、为什么、怎么改，并定位到具体字段。 |

## Red Flags
- 耗时操作无进度/骨架屏或结果反馈。
- 删除无二次确认、不可撤销。
- 同类操作在不同位置用不同词（保存/提交混用）。
- 只读项提交后才报错，错误信息缺「哪里/为什么/怎么改」。
- 高频路径超过 `3` 步或键盘不可用。

## Verification
- [ ] 耗时操作有进度/骨架屏，`>1s` 有反馈、`>10s` 说明还要多久。
- [ ] 可撤销/可返回、删除有二次确认、输入有草稿保护。
- [ ] 同类操作同词同位；危险操作用危险样式且不与主按钮相邻。
- [ ] 默认值合理、格式约束前置、只读项提前置灰。
- [ ] 选择项给可读标签、关键上下文可见；错误信息含「哪里/为什么/怎么改」并定位到字段。
- [ ] 高频路径 `≤3` 步、键盘可用（`Tab` 顺序合理、回车提交）、批量有全选与部分失败回执。
